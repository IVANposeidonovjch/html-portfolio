# Vinted → Telegram Monitor

Бот следит за твоими поисками Vinted и присылает новые объявления в личку,
в группу или в **конкретную тему (Topic)** группы.

```
Vinted search URL → Telegram group → Topic → новое объявление за секунды
```

Никаких фильтров внутри бота: фильтры ты настраиваешь на самом Vinted и просто
кидаешь ссылку. Всё, что стоит в URL (бренд, категория, размер, цена, состояние,
цвет, страна), передаётся в запрос как есть.

## Быстрый старт

```bash
cp .env.example .env         # вписать BOT_TOKEN от @BotFather и ADMIN_IDS
npm install
npm test                     # 172 офлайн-тестов логики
npm start
```

Docker:

```bash
docker compose up -d --build
```

## Как пользоваться

1. `/start` в личке бота.
2. **💳 Тариф** → Scout за 77 ⭐ ($1) на неделю. Без тарифа бот ничего не
   опрашивает и не даёт добавить ссылку — покупка и есть вход.
3. **➕ Добавить ссылку** → присылаешь URL поиска Vinted → даёшь название
   (`Raf`, `Helmut Lang`, `Bags`, `Avant mix`) → выбираешь, куда слать.
4. Группа и темы, по шагам (то же самое написано в `/help`):
   1) создай группу; 2) добавь бота админом с правом «Управление темами»;
   3) включи Topics в настройках группы и напиши там `/bind`; 4) готово —
   каждая новая ссылка заводит свою тему сама. Одна группа `Vinted Monitor`,
   внутри темы Raf / Helmut / Bags / Chanel.
5. Канал: добавь бота админом в канал и перешли боту любой пост оттуда.

Всё управление — инлайн-кнопки под сообщением бота; нижняя клавиатура не занимает
поле ввода. Кнопки перерисовывают то же сообщение, а не плодят новые.

Главное меню — четыре кнопки в сетке 2×2 и «Помощь» отдельной строкой под ней:

| Кнопка | Что делает |
|---|---|
| ➕ Добавить ссылку | мастер: URL → название → куда слать |
| 📋 Мои ссылки | список, вкл/выкл, переименовать, удалить |
| ⏯ Мониторинг | стоп-кран аккаунта, на кнопке видно текущее состояние |
| 💳 Тариф | что оплачено, сколько осталось, сравнение и покупка |
| ❓ Помощь | справка и второй уровень меню |

«Тариф» стоит в сетке, а не за «Помощью»: то, за что человек платит, — не
настройка. За «Помощью» остались 🌐 Язык и 👥 Мои чаты — их задают один раз.
Сама справка свёрстана разделами с примером того, как выглядит уведомление, и
нумерованной инструкцией по группам и темам.

### Картинки

Две: приветствие над меню в `/start` и фото-пример настоящего уведомления в
`/help` (подпись к нему рисует тот же `renderItem()`, что и боевые оповещения —
пример не может разойтись с реальностью). Когда картинка задана, текст справки
не дублирует пример словами, а коротко указывает на фото ниже; без картинки
остаётся текстовый макет.

Проще всего задать их прямо из Telegram, без доступа к серверу: как админ
отправь боту `/setstartimage` или `/sethelpimage` — ответом на фото либо командой
и следующим сообщением с фото. Бот скачает файл через file API, положит в том
`data/images/` и запомнит путь в базе, так что переживёт рестарт и пересборку
контейнера. Убрать: `/sethelpimage clear`.

Обе команды намеренно **не показываются ни в одном списке «/»**, включая
админский — они нужны пару раз за жизнь деплоя. Набранные руками работают.

Запасной вариант для чистой установки — `START_IMAGE` и `HELP_IMAGE` в `.env`
(ссылка или путь к файлу). То, что задано командой, имеет приоритет.

Из команд печатают только три: `/start`, `/add`, `/help`. Остальное — кнопками
(`/list`, `/chats`, `/pause`, `/resume`, `/plan`, `/lang` продолжают работать,
но в списке команд Telegram их больше нет). Отдельно: `/bind` — **внутри**
группы или темы; `/stats`, `/grant`, `/users`, `/userinfo <tg_id>` — только для
`ADMIN_IDS`, и видны они лишь в чатах админов.

## Архитектура

```
src/
  index.js              запуск: бот + планировщик + очередь отправки
  config.js             всё через переменные окружения
  db/                   SQLite (WAL): users, chats, topics, searches, дедуп, кэш
  vinted/
    url.js              search URL → канонические параметры каталога
    endpoints.js        известные адреса каталога, определяются в рантайме
    client.js           сессии-cookie, пул прокси, token bucket, backoff
    normalize.js        единая форма объявления
  monitor/
    scheduler.js        очередь по next_run_at, общий фетч, дедуп, priming
    sender.js           дорожка на чат, корзина токенов, ретраи 429
  bot/                  меню, мастер добавления, тарифы, платежи ⭐
  i18n/                 t(lang, key) и словари ru / en / de / uk
tools/                  probe.mjs и probe-standalone.mjs — снять живой контракт API
```

Ключевые решения:

* **Один запрос на N одинаковых поисков.** URL нормализуется в `canonical_key`
  (параметры отсортированы, повторы схлопнуты) — 10 пользователей с одним и тем
  же поиском Raf Simons стоят одного HTTP-запроса.
* **Ни одного дубля.** Первый проход только запоминает выдачу (baseline), дальше
  фильтр по `last_item_id` + таблица `seen_items(search_id, item_id)` +
  `sent_destinations(chat:topic, item_id)` — одно объявление в одну тему уходит
  один раз, даже если совпало с 10 ссылками.
* **Всплеск уходит сразу, и его размер — часть тарифа.** У каждого чата своя
  корзина токенов: первые `BURST_<ТАРИФ>` объявлений уходят подряд без пауз, и
  лишь потом чат переходит на устойчивую скорость (20/мин в группу, 60/мин в
  личку — это потолок Telegram, он не продаётся). Дорожки у чатов раздельные —
  притормозивший чат не держит остальные.

  | Тариф | Всплеск | 20 находок в группу | 30 находок |
  |---|---|---|---|
  | Scout / Hunter | нет | 60 с | 90 с |
  | Pro | 20 | **0 с** | 30 с |
  | Turbo | 30 | **0 с** | **0 с** |

  `BURST_FREE=1` и `BURST_BASIC=1` (Scout и Hunter) — это и есть «нет»: строго устойчивая
  скорость, по одному объявлению. Всплеск — то, что покупают, поэтому тариф со
  всплеском 1 вообще не упоминает всплеск в `/plan`, а не пишет «всплеск 1».
* **Разная скорость по тарифам.** Интервал берётся из плана пользователя
  (`INTERVAL_FREE/BASIC/PRO`) + джиттер, чтобы запросы не шли пачками.
* **Язык на пользователя.** Все строки живут в `src/i18n/locales/*`, язык
  берётся из Telegram при первом заходе и переключается кнопкой. Меню команд
  Telegram публикуется отдельным списком на каждый язык и на каждую область:
  `/bind` виден только в группах, админские команды — только в чатах админов. Тест следит,
  чтобы словари не расходились по ключам и плейсхолдерам.
* **Переезд в супергруппу переживается сам.** Включение тем превращает группу в
  супергруппу с новым chat id, и старые отправки падают навсегда. Бот ловит и
  служебное сообщение `migrate_to_chat_id`, и ту же подсказку внутри ошибки
  отправки — переносит поиски на новый id и досылает объявление.
* **Аккуратность к Vinted.** Token bucket на домен, ротация сессий и прокси,
  автоперелогин при 401/403, экспоненциальный backoff и cooldown IP при 429.

Технические ответы (скорость, прокси, стоимость 100/1 000/10 000 ссылок,
цена MVP) — в [`docs/TECH.md`](docs/TECH.md).

## Эндпоинт каталога и прокси

С 17.09.2026 каталог живёт по адресу `https://api.vinted.<tld>/svc-catalogue/items`
(старый `/api/v2/catalog/items` отдаёт HTML-404 даже при живой сессии). Проверено на
`.de` с резидентного IP. **Резидентный прокси обязателен**: тот же запрос с
дата-центрового IP получает 403, поэтому `PROXIES=` в `.env` — не оптимизация, а
условие работы. Адрес при этом не зашит в код:
`src/vinted/endpoints.js` держит список известных вариантов, клиент на старте
перебирает их, запоминает тот, что вернул объявления, и перебирает заново, если он
однажды отвалится. В логах это видно строкой `vinted endpoint for www.vinted.de: …`,
в `/stats` — колонкой endpoint.

Когда ни один вариант не отвечает, снимаем актуальный адрес с боевого IP. Проба
есть в двух видах: `tools/probe.mjs` (из репозитория, использует undici) и
`tools/probe-standalone.mjs` — один файл без зависимостей, его можно просто
скопировать на сервер, где нет ни `node_modules`, ни git:

```bash
PROXY=http://user:pass@host:port node tools/probe-standalone.mjs --selftest   # виден ли резидентный IP
PROXY=http://user:pass@host:port node tools/probe-standalone.mjs "https://www.vinted.de/catalog?search_text=raf+simons"
```

Скрипт пробует все варианты × два набора заголовков, показывает статус, тип контента,
ключи JSON и поля первого объявления, проверяет, лежат ли объявления прямо в HTML
страницы каталога (запасной путь), и — главное — прогоняет **проверку фильтров**:
тот же поиск с фильтрами и без, с обеими схемами параметров. Если выдача с
`brand_ids` совпала с выдачей без фильтров, значит фильтр молча проигнорирован, и
проба пишет это прямым текстом. Запускать её нужно на ссылке, где выбран бренд, —
иначе проверять нечего. Рабочий вариант фиксируется в `.env`:
`VINTED_API_STRATEGY=svc-catalogue-attrs`.

Замер 17.09.2026: поиск с `brand_ids=344976` в плоской схеме вернул объявление
adidas — фильтр принят и выброшен. Поэтому запросу с `*_ids` плоская схема
больше не предлагается вообще: лучше честная ошибка, чем чужой бренд в теме.

Ту же защиту делает и сам бот: ответ 200 с объявлениями не принимается как успех,
если бренды в нём противоречат фильтру — такой вариант отбрасывается и не
кешируется (`filtersLookHonoured` в `endpoints.js`).

### Бюджет пула

У пула есть счёт, и он считается, а не угадывается. Нагрузка — сумма
`1 / интервал` по **разным** `canonical_key` каждого домена: одинаковые поиски
делят один запрос, а темп задаёт самый быстрый тариф среди их владельцев.
Ёмкость — сумма безопасных ставок прокси: `PROXY_SAFE_RPS` перечисляет их по
одному числу на каждую запись `PROXIES` (у резидентного пула и одинокого
дешёвого IP безопасная ставка разная), всё неуказанное берёт
`PROXY_SAFE_RPS_DEFAULT=0.7`.

Дальше это работает не только как индикатор:

* **80 %** (`CAPACITY_WARN_PCT`) — предупреждение в лог;
* **90 %** (`CAPACITY_ALERT_PCT`) — личное сообщение админам, и ещё одно,
  когда нагрузка вернулась в норму. Повтор — не чаще `CAPACITY_REPEAT_MIN`;
* **100 %** — новый поиск не создаётся: пользователь получает «слоты заняты,
  попробуй через пару минут» вместо ссылки, которая молча опоздает. То же
  самое на возобновлении поставленного на паузу поиска. Поиск, который
  присоединяется к уже существующему `canonical_key` с не меньшей частотой,
  не стоит ничего и проходит всегда;
* новый поиск стартует не «сейчас», а в случайной точке своего интервала —
  десять регистраций за минуту не превращаются в десять одновременных
  запросов навсегда.

Текущие цифры — в `/stats`: нагрузка против ёмкости, разбивка по доменам и
занятые места по тарифам.

## Тарифы

| Тариф | Цена | Срок | Проверка | Ссылок | Всплеск | Мест |
|---|---|---|---|---|---|---|
| `locked` (пол) | — | — | не опрашивается | 0 | — | — |
| Scout | $1 (77 ⭐) | неделя, разово | 900 с | 2 | — | — |
| Hunter | $9 | подписка / 30 дней | 300 с | 25 | — | — |
| Ranger | $19 | подписка / 30 дней | 60 с | 100 | ⚡20 | — |
| Sniper Elite | $79 | подписка / 30 дней | 30 с | 300 | ⚡30 | 10 |
| `elite_max` | — | по /grant | 15 с | 1000 | ⚡50 | — |

Внутренние ключи остались `free/basic/pro/turbo` — переименование сломало бы
сохранённые строки; видимые названия живут в словарях. **`elite_max`** не
продаётся: цены нет, кнопки нет, в сравнении тарифов его нет — только
`/grant <tg_id> elite_max [дней]`.

**`locked` — пол, а не тариф.** Бесплатного тарифа больше нет: Scout — это
покупка на неделю, значит под ним должно было что-то лежать, иначе истекающий
Scout откатывался бы сам в себя и не истекал никогда. На полу новый аккаунт
оказывается сразу после `/start`, туда же попадает любой тариф, когда
оплаченное время кончилось. Поиски на полу **не опрашиваются вообще** — это
проверяется в самом SQL-запросе очереди, а не только при чтении профиля,
поэтому они останавливаются в момент истечения и запускаются сами, как только
тариф куплен. Сколько ссылок разрешено на полу — `LIMIT_LOCKED_SEARCHES`
(по умолчанию 0).

При первом запуске после этого изменения аккаунты, которые сидели на вечном
бесплатном `free`, переводятся на пол один раз (отметка `migrated_free_floor`
в `settings`). Тем, у кого ссылок больше нового лимита, `/plan` пишет об этом
прямой строкой: ничего не удалено, но новую добавить нельзя, пока не уберёшь
лишнюю.

### Подписки Telegram Stars

Hunter, Ranger и Sniper Elite продаются **настоящей подпиской**: Telegram сам
списывает звёзды каждые 30 дней, пока пользователь не отменит. Возвращаться в
`/plan` и покупать тариф заново не нужно.

Что это значит в коде:

* счёт создаётся через `createInvoiceLink` с `subscription_period` — у
  `sendInvoice` такого параметра нет вообще, поэтому подписка приходит ссылкой
  на кнопке, а не встроенным инвойсом;
* период жёстко равен **2 592 000 с (30 дней)** — другого Bot API не принимает.
  Отсюда же следует, что **Scout подпиской быть не может**: недельный пробник
  не тридцатидневная подписка, он остался разовой покупкой;
* каждое списание (и первое, и продление) приходит как
  `message.successful_payment` с `is_recurring`, а дату следующего списания
  берём из `subscription_expiration_date` — она авторитетнее любой, которую мы
  посчитали бы сами. Продление молчаливое: Telegram уже показал платёж;
* жизненный цикл — апдейт `subscription` (`state`: `canceled` / `failed` /
  `active`). Его **нет в `allowed_updates` по умолчанию**, он добавлен явно в
  `src/index.js`, иначе ни одно из этих событий до бота не доходит;
* отмена — `editUserStarSubscription(user_id, charge_id, is_canceled)`
  (в MTProto это `botCancelStarsSubscription`, в Bot API имя другое). Кнопка в
  `/plan` ничего не забирает: оплаченный период доживает до своей даты, и
  включить автопродление обратно можно там же;
* `failed` (не хватило звёзд) — не мгновенный отвал: тариф держится ещё
  `SUB_GRACE_HOURS` (48 по умолчанию), чтобы было время пополнить баланс.
  Отмене грейс не нужен — период и так оплачен до даты;
* смена тарифа отменяет предыдущую подписку **после** того, как прошёл новый
  платёж. Иначе Telegram спокойно списывал бы за обе сразу.

**Старые тарифы никуда не деваются.** У кого тариф куплен до подписок
(`sub_charge_id IS NULL`) — работает как работал, до своей даты, и `/plan`
честно пишет «Действует до», а не «продлевается». Миграции нет и не нужно: когда
период закончится, человек оформит подписку обычной кнопкой. Ничего не
переводится в подписку за спиной у пользователя — это списание денег, которого
он не просил.

**Места (`MAX_*_SEATS`)** — не маркетинг, а число, которое проверяется везде,
где тариф выдаётся: кнопка покупки пишет «мест нет», оплата звёздами
отклоняется в `pre_checkout` (деньги не списываются), а если последнее место
ушло, пока платёж был в пути, — возвращается через `refundStarPayment`.
`/grant` тоже упирается в лимит и называет настройку, которую надо поднять.
`0` = без ограничения.

Докупка **+10 ссылок** (`ADDON_*`) с продажи снята: плоская цена поверх любого
тарифа не отражала разницу в стоимости ссылки на быстром и на медленном тарифе,
а цена за ссылку для каждого тарифа своя — это сложнее, чем того стоит. Кнопки
и строки в `/plan` больше нет, код остался на месте: поставь
`ADDON_PRICE_STARS` — и предложение вернётся. Нужно больше ёмкости — это тариф
выше.

**Поддержка** — `/support` или кнопка в «Помощи»: сообщение уходит на
`SUPPORT_TG_ID` вместе с ником и id отправителя, ответ на это сообщение
автоматически возвращается пользователю.

**Достижение тарифа** отмечается отдельным сообщением: своя копия под каждый
тариф с настоящими числами (сколько ссылок, как часто проверка, какой всплеск) и
своя картинка — `TIER_IMAGE_*` или `/settierimage hunter|ranger|sniper|elite_max`
прямо из Telegram. Продление того же тарифа не празднуется.

**Сравнение с тарифом выше** в `/plan` считается из конфигурации: «проверка в 5×
чаще, ссылок в 4× больше, всего +$10». Пункт появляется, только если разница
реальна, — если интервалы совпадают, строки про скорость не будет. На верхнем
публичном тарифе предложения нет вовсе.

**Напоминание о скорости**: если объявление на момент доставки уже провисело
дольше `FOMO_AFTER_SECONDS`, к нему один раз в сутки добавляется строка о том,
сколько секунд было потеряно. Тарифам, которые и так доставляют мгновенно, она
не показывается. Оплата — Telegram Stars (`PRO_PRICE_STARS`, `BASIC_PRICE_STARS`);
пока цены не заданы, кнопки оплаты скрыты, планы выдаются вручную через `/grant`.

## Ограничения первой версии

* Только Vinted (Vestiaire / Willhaben / AutoBuy — следующий этап; слой
  `vinted/` изолирован именно под это).
* Vinted не даёт ни API, ни вебхуков — только опрос, поэтому задержка равна
  интервалу тарифа, а не нулю.
* SQLite достаточно до ~5–10 тысяч активных поисков; дальше — Postgres + Redis
  и несколько воркеров (см. `docs/TECH.md`).
